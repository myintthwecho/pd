## 1. Grounding Context

**Knowledge Source:**  
Synthetic refund-policy records authored for this assignment in `knowledge/refund-policy.json`. They are simplified platform policies, not a real merchant's legal policy. They encode the same business rules already enforced by the A6 guardrails, plus the return-window and evidence rules that were previously only implicit in the model instructions.

**Knowledge Records:**  
Nine records are available:

| ID | Title | Main trigger | Policy summary |
|---|---|---|---|
| `POL-DAMAGED` | Damaged on arrival | `damaged_on_arrival`, damage/photo keywords | Auto-approve when value ≤ 500 and evidence exists; otherwise manual review |
| `POL-NONDELIVERY` | Non-delivery with stalled tracking | `not_delivered`, tracking/parcel keywords | Auto-approve when tracking has not moved ≥ 14 days and value ≤ 500; if tracking shows delivery, do not auto-approve |
| `POL-NOT-AS-DESCRIBED` | Low-value item not as described | `not_as_described`, mismatch keywords | Auto-approve when value ≤ 500, within 30 days, with photos; otherwise manual review |
| `POL-RETURN-WINDOW` | Change-of-mind return window | `changed_mind` | Normal return only when ≤ 30 days and unused; used or late requests go to manual review |
| `POL-HIGH-VALUE` | High-value refund review | order value > 500 | Always manual review; the deterministic guardrail uses `HIGH_VALUE_OVERRIDE` |
| `POL-REPEATED-REFUND` | Repeated refunds and contradictory tracking | ≥ 3 prior refunds, dispute/tracking keywords | Use `FRAUD_RISK_FLAG` for deliberate bad-faith exploitation; weaker signals go to manual review |
| `POL-INCOMPLETE` | Incomplete or abusive claims | `other`, no-detail/abusive keywords | Manual review; do not auto-approve unverifiable claims; do not flag fraud without evidence |
| `POL-DUPLICATE` | Duplicate charge | `duplicate_charge`, duplicate-payment keywords | Auto-approve a low-value duplicate charge with evidence |
| `POL-PII` | PII handling | address/phone/card keywords | Redact personal data before the model call and in logs/screenshots |

The records are stored as JSON and loaded by `src/retrieval.ts`. No vector database is used.

**Retrieval / Selection Method:**  
Retrieval is deterministic and explainable:

1. **Primary score** (at least one primary signal is required):
   - claim reason matches a record: +5
   - each matching keyword in `claim_text`: +1, capped at 5
   - `order_value >= min_order_value`: +3
   - `prior_refund_count_30d >= min_prior_refund_count_30d`: +2
2. **Secondary score** (only added when a primary signal exists):
   - `order_value <= max_order_value`: +2
   - delivery age within a configured max/min range: +2
3. Keep records with score > 0, sort by score descending, break ties by record ID, and return the top 3.

Requiring a primary signal prevents a low-value order from retrieving unrelated policies merely because the value is below a threshold. Each returned record includes `score` and `matched` so the selection is auditable.

The JSON payload is what the harness/API uses for replay.

**Why the selected context is useful:**  
A6's instructions said to auto-approve claims that "match a normal refund policy," but the policy itself was not supplied to the model. T04 shows the consequence: a low-value, 21-day stalled non-delivery was conservatively sent to manual review. The non-delivery record makes the 14-day and 500-value conditions explicit, so the model has the information needed to distinguish a normal delayed parcel from a high-value or contradictory case. The records also make the high-value, return-window, and repeated-refund rules explicit without changing the deterministic guardrails. Because the records are small and locally selected, the approach is cheap, testable, and does not require a vector database.

## 4. One Controlled Improvement

**Selected Improvement:**  
Add retrieved refund-policy context to the model state (`policy_context`). This is one change: the model, question instructions, criteria, validation, guardrails, and fallback behaviour are unchanged between the baseline and grounded arms.

**Reason for Choosing It:**  
A6's only mismatch was T04, a low-value non-delivery with 21 days of stalled tracking. The model chose `MANUAL_INSPECTION_REQUIRED` even though the intended policy permitted auto-approval. The new baseline T02 shows the same information gap for a duplicate charge: the model chose `MANUAL_INSPECTION_REQUIRED` with 0.88 confidence even though `POL-DUPLICATE` permits auto-approval. T03 is also a miss, but at 0.38 confidence, so it is partly an uncertainty failure rather than a pure information gap. The instruction referred to a "normal refund policy" without supplying that policy. Grounding supplies the missing policy rather than adding a new deterministic rule, so the improvement targets the observed information gap and keeps the guardrails as the safety net.

**Before Configuration:**  
Baseline state is the A6 request only. The questions and criteria are unchanged in `config/jev-questions.json`. `buildJevRequest()` has no `policy_context` when no grounding is supplied.

**After Configuration:**  
`src/retrieval.ts` selects the top policy records and `classifyRefund()` attaches them as `policy_context`. `src/jevConfig.ts` includes the field in `state` only when records are present. Example payload: `eval/payloads/grounded/T04.json`. The test `test/grounding.test.ts` asserts that the baseline and grounded requests have identical `questions` and differ only by `policy_context`.

**Cases That Improved:**  
**T02 improved**: baseline `MANUAL_INSPECTION_REQUIRED` (0.88 confidence) → grounded `INSTANT_AUTO_APPROVE` (0.88 confidence), so the duplicate-charge policy context corrected a high-confidence information miss. **T03 improved**: baseline `MANUAL_INSPECTION_REQUIRED` (0.38 confidence) → grounded `INSTANT_AUTO_APPROVE` (0.97 confidence), so the not-as-described policy fixed both the choice and the confidence. **T04 improved (primary target)**: baseline `MANUAL_INSPECTION_REQUIRED` → grounded `INSTANT_AUTO_APPROVE` (0.97 confidence), so the non-delivery policy fixed the target miss. T01, T05, T06, T09, and T10 remain passes, so the added context has not caused a regression in the baseline-correct cases.

**Cases That Became Worse:**  
None. The main regression risks were T05 (return-window policy must keep the used, late item in manual review), T06 (high-value policy must keep the sofa in manual review), and T09/T10 (fraud/incomplete records must preserve the existing decisions); all four stayed correct.

**Trade-offs:**  
Grounding adds policy text to every model request, so it increases input tokens and may increase latency and cost in production. Retrieval also adds a component that can select stale, irrelevant, or incomplete policy records; the deterministic scoring and `matched` fields make this auditable, but they do not guarantee correctness. Both arms have one latency measurement per model case: baseline p50 467 ms and p95 753 ms; grounded p50 695 ms and p95 1052 ms. The descriptive p95 change is +299 ms (+39.7%), consistent with the longer grounded prompt, though one sample per case is not a stable repeated-run estimate. The new Playground responses include token usage for baseline T02/T03 and grounded T01–T10, but the six reused A6 cases did not, and the Playground does not expose per-request billing; cost therefore remains `N/A` for both arms. A stronger grounding record can also overfit the evaluation set: T04 informed the non-delivery record, so a held-out case is needed before claiming general improvement.

**Conclusion:**  
SUPPORTED: grounding raised accuracy from 7/10 (70%) to 10/10 (100%), fixing T02, T03, and the primary target T04 while preserving all seven baseline passes. The gain is +3 cases or +30 percentage points, with no worsened cases, but p95 latency rose from 753 ms to 1052 ms (+299 ms, +39.7%). Because the change is isolated to the model state and the deterministic guardrails remain in place, the result is consistent with the claim that explicit policy context fixes information-gap misses. The result is still not proof of production readiness: the evaluation set is small, six baseline cases lack captured confidence, latency is a single sample per case, and cost remains `N/A` for both arms. A shadow-mode rollout with a larger held-out set is the appropriate next step.

## 7. Engineering Reflection

**What I learned:**  
Systematic evaluation is different from a demo. Pre-registering expected results forced me to state the policy before seeing the model output, which made the T04 disagreement visible instead of letting me rationalise it after the fact. Separating the model decision from the deterministic guardrails also made the failure modes clearer: T07/T08 test the application layer, not the model, and should be evaluated separately. The A6 run also showed a measurement gap: confidence was not captured, so one guardrail could not be replayed later. For A7 I made the harness mark missing data as pending rather than filling it with an estimate.

**Why a few successful examples are insufficient:**  
A few successes mostly confirm that the happy path works. They do not cover edge cases, fallback behaviour, difficult or ambiguous claims, or regressions introduced by a change. A small sample can also be selected after the fact to look good, which hides systematic errors. In this evaluation, five of the ten cases are normal or easy; without the edge, fallback, and difficult cases, the T04 mismatch and the fallback paths would not be exercised. Ten cases is still small, so the result is evidence, not proof.
