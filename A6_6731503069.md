## 1. Problem and Capability

**Problem:**  
An online store receives refund requests as free-text claims. Support staff must decide whether to refund immediately, inspect the claim manually, or escalate it as suspected fraud. Handling every request manually is slow, while auto-approving everything exposes the business to refund abuse. The capability classifies each request into one of three risk decisions using the claim narrative plus a small amount of order context.

**Why AI?**  
The signal is in the narrative: genuine dissatisfaction ("the mug arrived broken"), logistics problems ("tracking has not moved for 21 days"), and bad-faith exploitation ("my fourth refund this month, tracking says delivered") can look similar at the field level. Deterministic rules on `claim_reason` or order value miss contradictions, urgency, and repeated-refund patterns expressed in language. A typed decision model can weigh those narrative signals while the application keeps deterministic control over the final action.

**Input:**  
A JSON object with synthetic order context and the claim text. Example:

```json
{
  "request_id": "T1",
  "order_id": "ORD-1001",
  "order_value": 48,
  "currency": "USD",
  "days_since_delivery": 2,
  "prior_refund_count_30d": 0,
  "claim_reason": "damaged_on_arrival",
  "claim_text": "The ceramic mug arrived in pieces. The box was crushed on one side and there is a photo of the damage attached to the ticket. I would like a refund for this order."
}
```

**Expected Output:**  
A structured decision with the selected choice, the full probability distribution, a confidence value, and a separate fraud signal:

```json
{
  "request_id": "T1",
  "decision": "INSTANT_AUTO_APPROVE",
  "model_decision": "INSTANT_AUTO_APPROVE",
  "confidence": 0.88,
  "probabilities": {
    "INSTANT_AUTO_APPROVE": 0.91,
    "MANUAL_INSPECTION_REQUIRED": 0.07,
    "FRAUD_RISK_FLAG": 0.02
  },
  "fraud_signal": 0.03,
  "fallback_used": false,
  "fallback_reason": null,
  "model": "typesafe/jev-1.13"
}
```

Possible choices: `INSTANT_AUTO_APPROVE`, `MANUAL_INSPECTION_REQUIRED`, `FRAUD_RISK_FLAG`.

## 2. Decision Implementation

**Decision Configuration / Code:**  
The Jev question configuration is in `config/jev-questions.json`. It defines one `choice` question and one `noul` question over the same state:

```json
{
  "model": "typesafe/jev-1.13",
  "questions": {
    "refund_risk": {
      "type": "choice",
      "instructions": "Classify the refund request into exactly one risk decision. Prefer MANUAL_INSPECTION_REQUIRED when the claim is ambiguous, incomplete, high value, or lacks verifiable detail. Use FRAUD_RISK_FLAG only when the narrative shows deliberate bad-faith exploitation, such as repeated refunds, contradictory tracking evidence, or threats to dispute a delivered order.",
      "criteria": {
        "INSTANT_AUTO_APPROVE": "Genuine, low-risk claim that matches a normal refund policy; a refund can be issued without human review.",
        "MANUAL_INSPECTION_REQUIRED": "Ambiguous, incomplete, high-value, or otherwise requires a human to inspect evidence before a refund decision.",
        "FRAUD_RISK_FLAG": "Signals of deliberate bad-faith exploitation of the refund process rather than genuine dissatisfaction."
      }
    },
    "fraud_signal": {
      "type": "noul",
      "instructions": "Does the claim show deliberate bad-faith refund exploitation rather than a genuine customer problem?",
      "criteria": {
        "false": "No deliberate fraud signal",
        "true": "Deliberate fraud signal present"
      }
    }
  }
}
```

The integration and fallback implementation is in `src/classifyRefund.ts`, with validation in `src/validate.ts` and guardrails in `src/policy.ts`. The full request used by the Playground is in `docs/api-examples.md`.

**Output Schema:**  
Allowed decisions: `INSTANT_AUTO_APPROVE`, `MANUAL_INSPECTION_REQUIRED`, `FRAUD_RISK_FLAG`.

Required fields: `request_id`, `decision`, `model_decision`, `confidence` (0–1), `probabilities` (all three choices, each 0–1, sum 1 ± 0.05), `fraud_signal` (0–1), `fallback_used`, `fallback_reason`, `model`.

**Validation Rules:**

| Stage | Rule |
|---|---|
| Input | `request_id` non-empty, at most 64 chars |
| Input | `order_id` matches `ORD-<4–32 uppercase alphanumeric/hyphen>` |
| Input | `order_value` is finite, greater than 0, at most 100,000 |
| Input | `currency` is a 3-letter uppercase ISO code |
| Input | `days_since_delivery` is `null` or an integer 0–365 |
| Input | `prior_refund_count_30d` is an integer 0–50 |
| Input | `claim_reason` is one of the six allowed enum values |
| Input | `claim_text` is 10–2,000 characters after trimming |
| Output | `answers.refund_risk.choice` is one of the three allowed decisions |
| Output | All three probabilities exist, are 0–1, and sum to 1 ± 0.05 |
| Output | `confidence` and `fraud_signal.noul` are 0–1 |
| Output | Missing, malformed, or unknown values trigger the fallback |

**Fallback Strategy:**  
The deterministic fallback is always `MANUAL_INSPECTION_REQUIRED`, which routes the request to a human support queue. This is safe because no refund is issued automatically and the request is not silently dropped.

| Condition | Fallback reason |
|---|---|
| Input schema invalid (model not called) | `INVALID_INPUT` |
| Timeout (4 s) | `TIMEOUT` |
| Network error, 5xx, 429 | `SERVICE_UNAVAILABLE` |
| Malformed JSON | `MALFORMED_RESPONSE` |
| Unknown choice, bad probabilities, missing fields | `INVALID_OUTPUT` |
| Auto-approval with `confidence < 0.55` | `LOW_CONFIDENCE` |
| Auto-approval with `order_value > 500` | `HIGH_VALUE_OVERRIDE` |
| Auto-approval with `fraud_signal >= 0.80` | `FRAUD_SIGNAL_OVERRIDE` |
| Model returns `FRAUD_RISK_FLAG` | Preserved and routed to the fraud team |

## 4. Engineering Reflection

**What worked:**  
The typed `choice` question simplified integration by returning a decision key and probability distribution directly. Separating `fraud_signal` added an independent safety check. The guardrails prevented risky or high-value transactions from being automatically approved, sending potential issues to manual review instead. The model also handled clear cases well, flagging the $2,400 sofa for manual review with 95% probability and identifying the repeated-refund claim as fraud with 89% probability.

**Unexpected behavior or mistakes:**  
T2 was the only mismatch: I expected instant approval for a 21-day delivery delay, but Jev chose manual inspection (56% vs. 43% for auto-approval). The wording about missing verifiable details likely pushed the decision toward review, making this a conservative error rather than a risky payout. T3 and T6 also had close results, showing that decision boundaries are not always clear. The two questions provided different signals, as T5 showed 89% fraud on the choice but only 56% on the independent fraud question. Finally, the Playground capture lacked the separate confidence value, so the low-confidence guardrail could not be verified.

**Production risks:**  
- **False auto-approvals** cost money directly; the high-value and confidence thresholds reduce but do not eliminate this.
- **Conservative false negatives** (as in T2) push genuine requests into the manual queue and raise support cost; the system is deliberately asymmetric, so this is the safer failure.
- **Distribution shift**: new refund scams and new product categories may not resemble the test cases.
- **Adversarial text**: customers can learn which phrases trigger auto-approval.
- **PII in free text**: claim narratives may contain names, addresses, or payment details that should be redacted before the model call.
- **Automation bias**: support staff may accept the classifier's label without independent review.
- **No rationale from the model**: the typed answer is actionable but not explainable, so disputes need the probability distribution and audit logs.
- **Cost and latency**: every request adds a model call; retries and timeouts must be bounded.
- **Policy drift**: thresholds such as $500 and 0.55 are business decisions that need periodic review.
- **Unlogged confidence**: if the confidence field is not captured alongside the choice, one of the guardrails cannot be audited later.

**Next improvement:**  
Add order and tracking evidence to the state (delivery scan, carrier status, return history, account age) so the model is not relying on narrative alone; that evidence would also help T2 distinguish a delay from a lost parcel. Capture and store the `confidence` value with every decision, calibrate the confidence threshold against a labelled sample of real decisions, add a human audit of a random slice of auto-approvals, redact PII before the call, and log every decision with its probabilities and fallback reason for later analysis. A shadow mode rollout (classify but do not act) would measure disagreement with human reviewers before enabling automatic payouts.
